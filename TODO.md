Verified in code (2026-08-01): `rankAttractions` (lines ~200-223) scores every attraction once, up front, using `distanceFromOriginMeters` (straight-line distance from the origin only) baked into each `ScoredAttraction`, then sorts once. `selectFeasibleAttractions` (lines 240-272) then walks that fixed, pre-sorted list top-to-bottom and — per attraction — computes `walkingMinutes` from that same frozen `distanceFromOriginMeters` (line 258-259, explicitly commented as "Rough walking time from previous stop (or origin) — this is a heuristic"), not from the previously *accepted* stop. - [x] **Preference learning runs before the clarification check — decided 2026-08-21: keep learning, and keep the flat boost. Measured against real Gemini, not reasoned.** Ariel's call on the first half was direct: do not gate learning on the clarification check, because losing signal is worse than learning from a vague sentence. The open half was whether the *boost* should be non-binary — a category inferred from a vague prompt worth less than one the walker stated with conviction — routed through something like `occurrencePreferenceBoost` (2 per occurrence, capped at 8) instead of the flat `PREFERRED_CATEGORY_BOOST` (+4), so weak evidence would have to accumulate before it was trusted. **It should not, and the reason is that `isUnderSpecifiedPrompt` is not a confidence signal about the preference at all.** It is a signal about `categoryNeeds`, which is a different field with a deliberately different definition: `PLACE_EXTRACTION_SYSTEM_PROMPT` sends a *taste* ("I love natural things") to `categoryNeeds []` and only a *request for a stop on this walk* to a category, while `PREFERENCE_EXTRACTION_SYSTEM_PROMPT` does the exact opposite — it emits only standing tastes, and is built end to end around "never guess, an empty list is the normal answer". The two passes are complementary by construction, so "under-specified AND a `like` was detected" does not select for weak evidence; it selects for explicit taste language, which is the highest-confidence evidence in the system and is exactly what the flat boost was written for. **17 real paired calls** (`extractPlaceNames` + `extractCategoryPreferences`, `gemini-flash-lite-latest`, 2026-08-21) bear that out, in three groups. (1) Five genuinely vague area-only prompts — "a walk in Tel Aviv", "bring me a walk in Zichron Yaakov", "תן לי טיול בעכו", "a nice walk in Tel Aviv", "a walk in Tel Aviv by the sea" — were all classified under-specified and all returned **no preference whatsoever**, so `saveCategoryPreferences` short-circuits on `detected.length === 0` and nothing is written at all. The scenario this entry describes, "a walk in Tel Aviv" being mined into `profiles.preferred_categories`, does not occur: there is nothing in the sentence to mine. (2) The only two under-specified prompts that learned anything learned a **dislike** — "walk me around Haifa, museums are boring" -> `museum:dislike`, "take me for a walk in Tel Aviv, I hate shopping" -> `shopping:dislike` — and a dislike never touches `PREFERRED_CATEGORY_BOOST`, because `mergePreferredCategories` removes the category from the array outright. There is no weight there to scale. (3) **The case that would have been mis-weighted is the one Ariel named as the strong one.** "I love museums, walk me around Jerusalem" returned `categoryNeeds ["museum"]` on 5 of 6 runs and `[]` on the sixth — the identical sentence, classified under-specified about one run in six purely on model variance in a field that has nothing to do with how convinced the walker sounds. (That rate matches the 4/5 and 8/9 already recorded further down this file for the same prompt shape.) Under the proposed change that sentence would be worth +4 five times and a weak accumulating boost the sixth, decided by noise. That is strictly worse than a flat boost — it adds variance, not calibration — and it would land on the one signed-in account that actually uses this app. **So nothing was built.** No code change, no migration, no new column; `learnPreferences(...)` stays where it is in `extract-places/route.ts`, awaited ahead of `clarificationFor(...)`, and `profiles.preferred_categories` keeps the flat +4. The design note at `PREFERRED_CATEGORY_BOOST` turns out to be right for a reason it does not state: the preference prompt is already the confidence filter, so everything that reaches the column is by construction the high-confidence kind, and there is no weak tier to build a weak path for. Adding a strength field to the preference schema would mean asking the model to start emitting the low-confidence preferences it is currently told to suppress, which is a change to what gets learned, not to how it is weighted. **What is only backed by the model's current behaviour:** all of the above is 17 samples on one model alias. If `gemini-flash-lite-latest` ever starts reading "I love museums" as a `categoryNeeds` less reliably, group (3)'s one-in-six becomes one-in-two and the argument gets stronger, not weaker — but if the preference pass ever starts emitting tastes it currently suppresses, this decision is worth re-measuring rather than assuming. **Still open, and it is the better version of this worry — needs Ariel, not a patch:** `profiles.preferred_categories` is monotonic and unbounded. Every `like` ever detected is appended, only an explicit `dislike` ever removes one, and each is worth a flat +4 forever with no recency or decay. A walker twenty prompts in can be carrying six preferred categories, at which point the preference signal means nothing because nearly everything is preferred, and the ranker's exploration branch is switched on against a set that no longer excludes anything. That is a real over-trusting problem, and it is the one the occurrence-scaled machinery would genuinely fit — a decay, or a cap on how many categories can carry the flat boost at once, or an occurrence count on the column so a category stated once ranks below one stated on five separate walks. It is a different entry from this one and a different decision. Original finding follows. **Preference learning runs before the clarification check** — in `src/app/api/extract-places/route.ts`, `learnPreferences(...)` is awaited at ~line 379, *before* `clarificationFor(...)` decides the prompt was too vague to act on. So "a walk in Tel Aviv" is mined into `profiles.preferred_categories` on the same request where the app admits it does not know what kind of walk was wanted. Arguably correct (the text is still signal), arguably wrong (we are learning from a prompt we just classified as under-specified). Needs a product decision, not a patch.

- [x] **Merged the place and fact extraction into one Gemini call (design doc step 11) — done 2026-08-20, and the measurement says it did not pay for itself.** A signed-in walker with learning on made three model-adjacent calls per prompt (`extractPlaceNames`, `extractCategoryPreferences`, `extractStandingFacts`); the first and third read the same sentence and are now one request, `extractPlacesAndFacts`. **Only that path merged.** A logged-out prompt still goes through `extractPlaceNames` with the smaller instruction and no `facts` field in the schema — that split *was* the stated reason the calls were separate, so undoing it would have made every anonymous prompt pay for a field nobody reads. **The category-preference pass was deliberately left alone**, for a reason stronger than "three at once is unwieldy": `walk-feedback` routes its comment box through `learnPreferencesFromText` where there are no places at all, so that function has to stand alone regardless — and keeping `preferences` out of the merged schema means a category liking has *nowhere to land* in the merged response. The boundary is enforced by the schema, not only by prompt text. `COMBINED_EXTRACTION_SYSTEM_PROMPT` is `PLACE_EXTRACTION_SYSTEM_PROMPT` and `FACT_EXTRACTION_SYSTEM_PROMPT` concatenated under two job headers, never a rewrite of either — a hand-merged third copy is a third definition of what a place and a fact are, and it goes stale the first time someone edits an original. That composition is what carries both halves of the separation rule across verbatim, and `tests/fact-extractor.test.ts` asserts containment of both source strings so it cannot quietly stop being true. One genuinely new block states the boundary the two calls used to enforce by *being two calls*. The `contents` carry **two** fact lists rather than one: `selectFactsForPrompt`'s picks under "Standing facts about this walker" (may steer the walk), and everything else still on record under "Older facts, for spotting a reversal only" (may only be contradicted). Folding them into one list would have silently undone step 9's scoring and let a year-old soft leaning steer walks again; dropping the second list would have made a demoted fact impossible to reverse. `learnFactsFromText` split into a read half and `storeExtractedFacts`, so the route hands over facts the merged call already returned instead of paying for a second extraction *and* a second `getStandingFacts`. 1087 tests green (was 1061), typecheck clean, lint unchanged (the same 1 pre-existing error + 3 warnings the clean tree has). Five mutations checked red on the right tests: dropping either half of the separation rule, folding the older facts into the steering list, having `storeExtractedFacts` ignore the list it was handed, dropping `facts` from the schema's `required`, and never taking the merged path.

(3) `"actually I eat meat again these days"` → `factContradictions` reported the reversal against `does not eat meat`, so `replaces` still works through the merged schema. (5) `"אני לא אוכל בשר, ואני תמיד עם הכלב"` → two facts, `places []`. **One real difference found, and it is small but real:** on `"I love food and museums, walk me around Jerusalem"`, a paired A/B run (5 requests each, same session, same empty fact state, `learnPreferences:false` taking the unmerged path and `true` taking the merged one) gave `categoryNeeds ["food","museum"]` **5/5 on the unmerged path and 4/5 on the merged one**, the fifth returning `[]`. - [x] **Cost and latency, measured before and after (2026-08-20) — the merge costs ~13% more, not less.** Method: a temporary `console.log` around every `client.models.generateContent` call reporting `ms` and the SDK's `usageMetadata` token counts, plus browser-side wall clock on the full `/api/extract-places` response, over the same three prompts with `standing_facts` reset between runs. Instrumentation removed before the commit. **Calls per prompt: 3 → 2.** Medians per prompt (signed-in, learning on, nothing on record): **before** `extractPlaceNames` 2108 in / 79 out / 964 ms, `extractCategoryPreferences` 375 / 16 / 608 ms, `extractStandingFacts` 537 / 9 / 638 ms — **3020 input, 104 output**; **after** `extractPlacesAndFacts` 3059 / 85 / 1091 ms, `extractCategoryPreferences` 372 / 28 / 728 ms — **3431 input, 113 output**. So input tokens **+411 (+13.6%)** and output **+9 (+8.7%)**. The input grew because the merged instruction is not the two prompts' *sum* — it is their sum plus ~418 tokens of new text stating the boundary that being two separate requests used to enforce for free. At `gemini-3.5-flash-lite`'s published $0.30/M input and $2.50/M output (the alias `gemini-flash-lite-latest` currently resolves to; **treat the dollar figure as indicative — the token counts are measured, the price was read off a pricing page and Google moves these**), that is **$0.001166 → $0.001312 per prompt, +12.5%**, or roughly $1.17 → $1.31 per thousand prompts. **Latency did not improve either.** The eliminated fact call was never on the critical path alone — it ran inside a `Promise.all` alongside the preference call, so removing it saved `max(608, 638) - 608 ≈ 30 ms`, while the merged call is ~127 ms slower than the place call it replaced. Gemini time on the critical path: **~1.60 s → ~1.74 s**. End-to-end wall clock agrees, flat to slightly worse: `"I don't eat meat, take me to Habima Square"` 3402/3121 ms before vs 3577/3424/3145 after; `"bring me a walk in Zichron Yaakov"` 3162/3045 before vs 4203/3096 after. (The third prompt, `"I love food and museums…"`, ran 4.4–16.7 s in both arms — Overpass dominates it and it measures nothing about Gemini.) **What the merge actually buys:** one fewer HTTP round trip per prompt, which is not nothing — the baseline measurement round itself died with three `500`s when 6 prompts × 3 calls tripped the free-tier rate limit, and 2 calls/prompt is a third less pressure on that quota — plus one fewer Supabase read (`learnFactsFromText`'s internal `getStandingFacts` is gone). **Open decision for Ariel:** step 11's stated trigger was "merge if the second call proves costly", and measured, it was not — it was the cheapest of the three (537 in / 9 out). Keeping the merge is defensible on request count and quota headroom; reverting it is defensible on cost and latency. Most of the +411 tokens is the separation block, and trimming that is the one saving that should *not* be taken, since it is the text protecting the rule this whole merge was warned about.

- [x] **Retry with backoff on the Gemini calls — done 2026-08-21.** Named as the right fix in the revert decision above, and it did not exist at all: every `client.models.generateContent` in `gemini-client.ts` was bare, and the benchmark run that decision rests on died with three real `500`s. All four calls now go through one private `withGeminiRetry` in that file — `extractPlaceNames`, `resolveCanonicalName`, `extractCategoryPreferences`, `extractStandingFacts` — and nothing else changed; no call site was touched. **Policy:** 3 attempts, retried only on 429 or 5xx. A 400/401/403 throws on the first attempt, because a request the API rejects as malformed fails identically on every retry and spending the budget on it only makes the same error arrive later — not hypothetical here, `gemini-3.5-flash-lite` answers 400 to `thinkingConfig` (see the comment in `extractPlaceNames`). An error with no readable status is not retried either: only what can be positively identified as transient gets a second try. **Backoff is equal jitter** — a 600ms window doubling each retry, and the wait is half the window plus a random draw over the other half, so 300–600ms then 600–1200ms. The fixed half guarantees each retry really does wait longer than the one behind it; the random half is the part that matters under real rate-limiting, since a fixed interval is exactly what turns one 429 across concurrent requests into a synchronized retry storm. **Total-latency cap 10s**, measured from the first attempt and checked before each sleep: a new attempt does not start if the wait would cross it. Picked against the measured numbers above rather than as a round guess — the place call runs ~1s at the median, so a full three-attempt chain lands near 5s and the cap only bites when the attempts themselves run long. 10s and not the 120s of `WALK_PLAN_TIMEOUT_MS` because the two waits are not alike: a walk build is a foreground action the walker chose and is watching a skeleton for, while this sits in front of the prompt box with nothing on screen, and `PlacePromptPanel`'s fetch carries no `AbortController` of its own, so the browser still owns the outer ceiling exactly as it did for `/api/walk-plan` before `69966f7`. **What the cap does not do:** it stops a *new* attempt from starting, it cannot cut short one already in flight, because no per-request timeout is set on the SDK today (`httpOptions.timeout` would be the place). A single hung request still hangs — the budget bounds what retrying adds, not what was already there. Deliberately no separate per-delay ceiling: at 3 attempts the longest sleep is 1.2s, so a cap above that would be a constant that can never run, and the budget is what actually bounds the growth. **Error shape read out of the SDK, not guessed:** `@google/genai` 2.13.0 throws its own `ApiError` with the numeric HTTP status as a top-level `status` property (`throwErrorIfNotOK` in `dist/index.mjs` builds it for anything 400–599), and the `message` is the entire error body JSON-stringified — so the status is the field to read and the message is not worth parsing. Read structurally (`typeof error.status === "number"`) rather than through `instanceof ApiError`, which would have forced every test that mocks `@google/genai` to hand back a real SDK class instead of a plain rejection. **Caller contract unchanged:** the last error is rethrown exactly as it arrived, so `learnPreferencesFromText` and `learnFactsFromText` still swallow it into their fallbacks, `canonicalNameFor` still answers null, and a failed place extraction still fails the request. Retries delay that outcome, they do not soften it. **Tests** in `tests/gemini-client.test.ts` (10 new, 1072 green, typecheck clean, lint unchanged — the same 1 pre-existing error + 3 warnings): a 429 then success, a 500 then success, the preference call retrying too (the wrapper is shared, not bolted onto the place call alone), exhaustion rethrowing the identical error object after exactly 3 calls, 400 / 403 / no-status each failing on the first call, the backoff growing 450ms → 900ms with `Math.random` pinned mid-window, jitter producing two different waits from two draws of the same window, and the budget refusing a second attempt after a 9.8s failure. Fake timers throughout — nothing in the suite sleeps for real. Six mutations checked red on the right tests: retrying 400, disabling the budget check, dropping the jitter, dropping the doubling, leaving the preference call unwrapped, and raising `MAX_ATTEMPTS` to 5. **Not verified live, and it cannot be from here:** every failure above is a fabricated rejection with a `status` on it. What a mocked 429 cannot show is whether the free tier's real rate limit clears inside a ~2s backoff, or whether it wants the `RetryInfo` hint Google returns with some 429s — which this ignores in favour of its own schedule. Confirming either needs a genuinely rate-limited account and a burst fired at it, the same kind of gap as jsdom-fake vs. real-database elsewhere in this file. The broader Post-MVP item ("Rate limiting/retries with backoff for upstream APIs") stays open: ORS, Overpass and Nominatim are still bare.
